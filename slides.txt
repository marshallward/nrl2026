Challenges
==========

Porting MOM6 is not just a performance problem.

.. list-table::
   :widths: 30 70

   * - **Code size**
     - ~200k lines of Fortran

   * - **Continuity**
     - Answer changes disrupt ongoing research

   * - **Complexity**
     - Many algorithms and customizations

   * - **Operational**
     - The CPU path must remain viable

Can we add GPUs without disrupting the model?


Porting Strategy
================

.. list-table::
   :widths: 24 10 66

   * - **Preserve**
     - →
     - Keep MOM6 Fortran as the source of truth

   * - **Compute**
     - →
     - Kernelize solvers for remote calculation

   * - **Data**
     - →
     - Control flow of data between host and device

   * - **Verify**
     - →
     - Reproducible results and CPU performance

``do concurrent``
=================

Fortran language feature to promote loop parallelization.  Execution may occur
in any order:

.. "The execution order of the iterations can be left indeterminate..."

.. The block of a DO CONCURRENT construct is executed for every active
   combination of the index-name values.  Each execution of the block is an
   iteration. The executions may occur in any order.

.. list-table::
   :widths: 48 1em 50

   * - .. code:: fortran

          do j=1,nj ; do i=1,ni
              a(i,j) = b(i,j) + c(i,j)
          enddo ; enddo

     - ⇒

     - .. code:: fortran

          do concurrent (j=1:nj, i=1:ni)
              a(i,j) = b(i,j) + c(i,j)
          enddo

Results cannot depend on loop order or system state:

* ``a(i) = a(i-1) + 1``

* ``sum = sum + a(i)``

* ``print *, i``


.. ``do concurrent`` kernel
   ========================

   CUDA C++

   .. code:: c++

      // Define kernel
      __global__ kernel(a, b, c, ni, nj, nk) {
           i = blockIdx.x * blockDim.x + threadIdx.x;
           j = blockIdx.y * blockDim.y + threadIdx.y;
           k = blockIdx.z;

          a(i,j,k) = b(i,j,k) + c(i,j,k);
      }

      // Submit kernel
      kernel<<< grid, block >>>(a, b, c, ni, nj, nk);

   Fortran ``do concurrent``

   .. code:: fortran

      do concurrent (k=1:nk, j=1:nj, i=1:ni)
          a(i,j,k) = b(i,j,k) + c(i,j,k)
      enddo


Why ``do concurrent``?
======================

Single Codebase
   Can generate serial, threaded, or GPU bytecode

Platform Independence
   Compilers can target their respective platforms (NVIDIA ⇒ CUDA, AMD ⇒ ROCm)
   
Algorithmic Precision
   Compilers can make better optimization choices


NVIDIA's ``do concurrent``
==========================

.. code:: fortran

   do concurrent (k=1:nz, j=js:je, i=is:ie)
     a(i,j,k) = b(i,j,k) + c(i,j,k) + d(i,j,k)
   enddo

is translated into an OpenACC kernel

.. code:: fortran

   !$acc parallel loop collapse(3) vector_length(128)

   do k=1,nz ; do j=js,je ; do I=is,ie
     a(I,j,k) = b(i,j,k) + c(i,j,k) + d(i,j,k)
   enddo ; enddo ; enddo

   !$acc end parallel loop

Loops are broken into "gangs" of 128

.. vector length is compiler or hardware-dependent

Nested ``do concurrent``
------------------------

.. this probably goes later, if at all

Nested ``do concurrent`` can launch with dynamic grid and block geometries.

.. code:: fortran

   do concurrent (j=jsh:jeh)
     do concurrent (k=1:nz, I=ish-1:ieh)
       u_cor(I,j,k) = u(I,j,k) + du(I,j) * visc_rem_u(I,j,k)
     enddo
   enddo

For a 256 × 256 × 100 domain:

* Grid: (804,66,1)
* Block: (32,4,1)

804 × 32 comprises the ``i-k`` loop, 66 × 4 the ``j`` loop


A second example
----------------

.. This is probably far too abstract

256 × 256 × 100 kernel geometry is (9,64,1) × (32,4,1)

.. code:: fortran

   do concurrent (j=js:je)
     do k=1,nz
       do concurrent (I=is-1:ie)
         uhbt(I,j) = uhbt(I,j) + uh0(I,j,k)
         ubt(I,j) = ubt(I,j) + CS%frhatu(I,j,k) * u_uh0(I,j,k)
       enddo
     enddo
   enddo

Threads across ``i``, serial reproducible sums in ``k``, dispatched in blocks
along ``j``.

.. 
   possible explanation

    nj = 64*4 = 256

    ni = 9*32 = 288 <- 257 rounded up to next 32-step


Data Transfer?
==============

*Fortran does not prescribe data movement!*

======== ==================================
Managed  ``allocate()`` management
Unified  Automatic management of all memory
Separate Manual memory management
======== ==================================

For portability, we do **manual** and use **OpenMP**



Memory Management
=================

Move memory to device

.. code:: fortran

   !$omp target enter data map(alloc: a) map(to: b, c)

Execute kernel

.. code:: fortran

   do concurrent (k=1:nk, j=1:nj, i=1:ni)
       a(i,j,k) = b(i,j,k) + c(i,j,k)
   enddo

Return result to host

.. code:: fortran

   !$omp target exit data map(from: a) map(delete: b, c)


Strategy
========

Move the entire problem to the GPU
   Avoid expensive data transfers, at high mem cost

Manual memory management
   At least until unified memory is an option

``do concurrent`` if we can, OpenMP if we must
   (... and OpenACC as a last resort)

Local arrays
============

NVIDIA's ``do concurrent`` can't (yet) use local arrays

.. code:: fortran

   !$omp target teams loop collapse(2) private(c1)
   do j=js,je ; do i=is,ie ; if (mask(i,j) > 0.) then
     b_denom_1 = h(i,j,1) + a(i,j,1)
     b1 = 1. / (b_denom_1 + a(i,j,2))
     d1 = b_denom_1 * b1
     visc_rem(i,j,1) = b1 * h(i,j,1)

     do k=2,nz
       c1(k) = a(i,j,k) * b1
       b_denom_1 = h(i,j,k) + (a(i,j,k) * d1)
       b1 = 1. / (b_denom_1 + a(i,j,k+1))
       d1 = b_denom_1 * b1
       visc_rem(i,j,k) = (h(i,j,k) + a(i,j,k) * visc_rem(i,j,k-1)) * b1
     enddo

     do k=nz-1,1,-1
       visc_rem(i,j,k) = visc_rem(i,j,k) + c1(k+1) * visc_rem(i,j,k+1)
     enddo
   endif ; enddo ; enddo

For now, OpenMP is a portable alternative.


Derived Types
=============

Derived types and their arrays are handled separately.

.. code:: fortran

   !$omp target enter data map(to: G)
   !$omp target enter data map(to: G%dxT, G%dxCu, G%dxCv, G%dxBu)

Care must be taken when updating derived types

.. code:: fortran

   ! Transfer CS and its scalars
   !$omp target enter data map(to CS)

   ! Set up CS arrays
   !$omp target enter data map(to: CS%a_u, CS%a_v)
   !$omp target enter data map(to: CS%h_u, CS%h_v)

   ! This would overwrite CS pointers and lose array data!
   !$omp target update to(CS)


No Objects on GPUs
==================

Dynamic object-oriented constructs are volatile

.. code:: fortran

   class(EOS_base), allocatable :: type

.. code:: fortran

   procedure(i_density), deferred :: density

.. code:: fortran

   real elemental function density_linear(this, T, S, p)
     class(EOS), intent(in) :: this
     real, intent(in) :: T, S, p

     density_elem_linear = this%Rho_T0_S0 + this%dRho_dT * T &
         + this%dRho_dS * S + this%dRho_dp * p
   end function density_linear

..
  Switch to OpenACC?
  ==================
  
  OpenMP was chosen for portability, but there are occasional issues.
  
  * "``!$omp target``" and "``do concurrent``" can clash
  
  * No ``"worker"`` abstraction prevents 2D thread geometries.
  
  * Missing features like ``async``  (``nowait``)


Summary
=======

Can we preserve codebase?
   Yes! ``do concurrent`` with OpenMP is viable

Bit reproducible?
   Yes!  CPU and GPU match on NVIDIA

Retain CPU performance?
   Yes! And with GPU speedups

..
  Upcoming challenges
  -------------------
  
  * The next milestone (``benchmark``) touches many of the above issues.
  
  * We cannot write diagnostics!  MOM6 has a complex diagnostic manager which
    will require complex design decisions.
  
  * The ultimate goal is GFDL's OM5 configuration.
  
    * By this point, each respective group could be working on their own
      configuration of interest!
